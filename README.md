# 🔎 LinksAnalyzer — асинхронный анализатор веб-страниц на FastAPI

## 📋 Краткое описание
__LinksAnalyzer__ — backend-сервис для асинхронного анализа веб-страниц на `FastAPI` 
с использованием `aiohttp`, `Celery`, `Redis`, `PostgreSQL` и `SQLAlchemy Async`.

Сервис предназначен для:
- массовой проверки доступности URL;
- сбора технических характеристик страниц;
- анализа содержимого HTML;
- выявления ошибок обработки;
- подготовки данных для дальнейшей аналитики и мониторинга;
- тестирования собственных сервисов.

---

## 🚧 Статус проекта

Проект находится в стадии __MVP__.

__Реализовано__:
- создание и фоновая обработка задач анализа;
- асинхронная загрузка страниц;
- HTML-парсинг;
- сохранение результатов в PostgreSQL;
- Redis cache успешных результатов;
- публичный API задач и результатов;
- Ops API для диагностики.

__Ближайшие этапы__:
- автоматические тесты;
- полноценный pipeline обработки.

## ❓ Зачем нужен LinksAnalyzer

При разработке и сопровождении backend-сервисов часто возникает необходимость быстро проверить набор веб-страниц 
или HTTP endpoints:
- доступен ли URL;
- какой HTTP-статус возвращает ресурс;
- сколько времени занимает ответ;
- какой объем HTML возвращается;
- содержит ли страница базовые metadata;
- возникают ли ошибки при загрузке или обработке отдельных URL.

Если URL много, это становится неудобно: проверки нужно повторять, а результат должен быть сохранен и доступен позже.

__LinksAnalyzer__ решает эту задачу, превращая набор URL в управляемую задачу анализа
с сохранением статуса, прогресса и результатов обработки набора URL.

---

## 🎯 Идея проекта

__LinksAnalyzer__ ── backend-сервис для асинхронного анализа веб-страниц и HTTP endpoints.

Сервис принимает список URL, создает задачу анализа, выполняет обработку в фоне через Celery worker 
и позволяет получать статус и результаты через API. Для повторных проверок успешные результаты кэшируются в Redis.

ℹ️ Проект предназначен как внутренний инструмент для технической проверки собственных сайтов, 
API endpoints и backend-сервисов.

Типовые сценарии применения:
- smoke-check собственных сайтов и endpoints после изменений;
- быстрая проверка доступности набора URL;
- сравнение времени ответа разных страниц;
- выявление URL, которые возвращают ошибочные HTTP-статусы;
- проверка наличия базовых HTML metadata;
- подготовка данных для дальнейшего мониторинга или отчетности.

## ⚙️ Ключевые возможности

### Массовый анализ URL

- создание задачи анализа по списку URL;
- нормализация входных адресов;
- сохранение задачи и результатов в PostgreSQL;
- получение статуса и результатов через API.


### Асинхронная загрузка страниц

- конкурентная загрузка страниц через `aiohttp`;
- ограничение количества одновременных HTTP-запросов;
- timeout для внешних запросов;
- ограничение максимального размера ответа;
- проверка поддерживаемого `content-type`;
- обработка сетевых ошибок без остановки всей задачи.


### HTML-парсинг

- выполнение парсинга через `BeautifulSoup` и `lxml`;
- извлечение `title` и `description`;
- подсчет ссылок и изображений;
- выполнение HTML-парсинга через `ThreadPoolExecutor`, чтобы не блокировать event loop во время синхронной обработки HTML.


### Фоновая обработка

- запуск анализа через `Celery worker`;
- использование `Redis` как broker/backend для Celery;
- отсутствие блокировки HTTP-запроса во время анализа.


### Отслеживание прогресса

- хранение статуса задачи;
- подсчет обработанных URL (`processed_urls`);
- расчет процента выполнения (`progress_percent`);
- возможность отдельно запрашивать состояние задачи через API;
- обновление прогресса по мере обработки URL, без ожидания завершения всей задачи.


### Redis cache

- кэширование успешных результатов анализа URL;
- TTL для кэшированных данных;
- версионирование cache keys;
- метка `cached=true` в результатах;
- ошибки Redis не блокируют и не останавливают анализ.


### Ops API

- health-check приложения;
- проверка доступности PostgreSQL;
- проверка доступности Redis;
- проверка доступности Celery;
- ручной debug-запуск обработки задачи.

## 🏗️ Архитектура проекта

### Технологический стек
- __Основной Backend-стек__: `Python 3.12+` + `FastAPI` + `Pydantic`
- __Стек базы данных__: `PostgreSQL` + `Alembic` + `SQLAlchemy Async ORM`
- __Загрузчик URL__: `aiohttp` + `asyncio`
- __Парсинг HTML-страниц__: `BeautifulSoup` + `lxml` + `ThreadPoolExecutor`
- __Фоновое выполнение__: `Celery` + `Redis`
- __Кэширование__: `Redis`
- __Деплой__: `Docker` + `Docker Compose`
- __Тестирование__: `pytest`


### Структура приложения

```text
app/
├── analyzer/
│   ├── api/                 # API анализа
│   ├── repositories/        # Работа с AnalysisTask и WebsiteResult
│   ├── schemas/             # Pydantic-схемы API
│   ├── services/            # Бизнес-логика анализа
│   ├── cache.py             # Redis cache результатов анализа
│   ├── celery_tasks.py      # Celery задача
│   ├── dto.py               # DTO результатов
│   ├── fetcher.py           # aiohttp-загрузчик
│   ├── models.py            # SQLAlchemy-модели
│   └── parser.py            # HTML-парсер
├── core/
│   ├── config.py            # Настройки приложения
│   └── redis.py             # Redis clients
├── db/                      
│   ├── base.py              # Базовый класс SQLAlchemy-моделей
│   ├── session.py           # AsyncEngine и сессии FastAPI
│   └── worker_session.py    # Отдельные DB-сессии Celery worker
├── ops/                     # служебные endpoints
├── worker/                  # Celery application
└── main.py                  # FastAPI application
```

## ▶️ Быстрый старт

### 1. Клонировать репозиторий

```bash
git clone <repository-url>
cd LinksAnalyzer
```

### 2. Создать `.env`

```bash
cp .env.example .env
```

### 3. Запустить контейнеры

```bash
docker compose up --build
```

### 4. Применить миграции

В отдельном терминале:
```bash
docker compose exec app alembic upgrade head
```

После этого приложение будет доступно локально:
- __API__: `http://localhost:8000`
- __Swagger__: `http://localhost:8000/docs`

## 🌐 API endpoints

### Public API
```text
POST /api/v1/analyze
GET  /api/v1/tasks
GET  /api/v1/tasks/{task_id}
GET  /api/v1/tasks/{task_id}/results
```

### Ops API
```text
GET  /api/ops/health
GET  /api/ops/health/db
GET  /api/ops/health/redis
GET  /api/ops/health/celery
GET  /api/ops/health/full
POST /api/ops/tasks/{task_id}/fetch
```

⚠️ `POST /api/ops/tasks/{task_id}/fetch` используется как служебный endpoint для диагностики 
и ручного запуска обработки задачи.

ℹ️ Основной production-like flow использует Celery worker после `POST /api/v1/analyze`.


Подробное описание API находится в [API](./docs/API.md).

## 🚧 Ограничения

Текущая версия является MVP и не претендует на полноценный crawler или monitoring platform.

Текущие ограничения:
- нет авторизации;
- нет rate limiting;
- нет robots.txt handling;
- нет sitemap.xml support;
- нет recursive crawling;
- нет retry policy для отдельных URL;
- нет scheduled analysis через Celery Beat;
- нет полноценного monitoring/alerting;
- не выполняется JavaScript rendering;
- не обрабатываются сайты, требующие авторизации или CAPTCHA.

Эти ограничения не включены в __MVP__ и будут реализовываться в будущем.
