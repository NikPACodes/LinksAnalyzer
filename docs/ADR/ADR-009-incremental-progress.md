# ADR-009: Периодическое сохранение прогресса анализа

---

## Причина
Анализ большого количества URL может занимать продолжительное время.

Если сохранять состояние задачи только после обработки всех URL, 
`API` не сможет отображать актуальный прогресс выполнения — значение `processed_urls` в PostgreSQL 
будет обновлено только после завершения анализа.

С другой стороны, выполнение `commit` после каждого обработанного URL 
создает лишнее количество транзакций и увеличивает нагрузку на PostgreSQL.

Необходим компромисс между актуальностью `live progress` и количеством операций фиксации транзакций.

---


## Принятое решение
Прогресс анализа сохраняется в PostgreSQL инкрементально по мере обработки URL.

После обработки каждого URL сервис обновляет:
- соответствующий `WebsiteResult`;
- счетчик `processed_urls` задачи.

Результат и изменение счетчика фиксируются в одной транзакции:
```text
Cache HIT   или   Fetch -> Parse
             ↓
Обновление WebsiteResult   ->   обновление processed_urls
             ↓
Промежуточный commit -> данные доступны через API
```

Чтобы уменьшить количество коммитов, изменения накапливаются. 
В текущей реализации `commit` выполняется, когда число обработанных URL __кратно пяти__ 
либо с предыдущего `commit` прошло __не менее двух секунд__.

Переход в `processing` фиксируется перед обработкой. 
После завершения анализа оставшиеся изменения сохраняются вместе со статусом `done`.

Результаты из кэша и сохраненные ошибки отдельных URL также учитываются в прогрессе. 
`progress_percent` вычисляется из `processed_urls` и `total_urls` при формировании API-ответа.

---


## Результаты

### Положительные
- прогресс и результаты доступны до завершения всей задачи;
- уменьшается количество `commit` по сравнению с фиксацией после каждого URL;
- ограничивается объем прогресса, который может быть потерян при аварийном завершении worker;
- статус задачи сохраняется независимо от полного времени выполнения анализа.

### Отрицательные
- коммитов больше, чем при единственном сохранении в конце;
- видимый прогресс может отставать от фактической обработки;
- появляются дополнительные параметры управления частотой commit;
- при ошибке задача может содержать частичные результаты.

### Ограничения
Условие `commit` проверяется после обработки очередного результата. 
Интервал в две секунды не является гарантией обновления с такой периодичностью.

Изменения между двумя `commit` остаются частью незавершенной транзакции 
и при аварийном завершении worker могут быть потеряны.

Прогресс отражает количество обработанных URL, а не число успешных загрузок или оставшееся время.

## Заметки

`Live Progress` строится на данных приложения, сохраненных в PostgreSQL, а не на состоянии `Celery task`.
Это позволяет получать состояние анализа через обычный API независимо от механизма запуска фоновой задачи.

Текущие значения `commit_every` и `commit_interval_seconds` могут быть вынесены 
в `application settings` при необходимости контроля конфигурации сохранения прогресса.

- [ADR-004](./ADR-004-fetch-live-progress.md) — получение результатов загрузки по мере готовности.
- [ADR-005](./ADR-005-html-parsing-threadpool.md) — парсинг перед сохранением результата.
- [ADR-007](./ADR-007-celery-background-processing.md) — фоновое выполнение анализа и хранение состояния задачи независимо от Celery.
- [ADR-008](./ADR-008-redis-cache.md) — получение готового результата из кэша.

## Возможные альтернативы

### Единственный commit в конце анализа
__Преимущества__:
- минимальное количество транзакций;
- все изменения анализа фиксируются одной транзакцией.

__Недостатки__:
- промежуточный прогресс не отслеживается;
- сбой до `commit` откатывает все накопленные изменения.

### Commit после каждого URL
__Преимущества__:
- результат доступен сразу после обработки URL;
- минимальная потеря уже обработанного прогресса при аварийном завершении `worker`.

__Недостатки__:
- дополнительная нагрузка на PostgreSQL;
- большое количество транзакций.
