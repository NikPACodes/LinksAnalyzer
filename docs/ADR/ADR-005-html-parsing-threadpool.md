# ADR-005: Вынос HTML-парсинга из Event Loop

---


## Причина

После загрузки страницы анализатор выполняет HTML-парсинг с использованием `BeautifulSoup`.  
В отличие от HTTP-запросов, парсинг HTML является синхронной операцией, следовательно,  
выполнение парсинга непосредственно внутри `asyncio event loop` может привести к: 
- блокировке `event loop`:
- задержке выполнения других HTTP-запросов; 
- задержке работы других async-задач;
- задержке обработки результатов анализа.

При этом на этапе __MVP__ полноценный конкурентный pipeline обработки URL создает дополнительную сложность 
и не является целесообразным.

---


## Принятое решение

Вынести _синхронный_ HTML-парсинг из `asyncio event loop` в отдельный поток через `ThreadPoolExecutor`.

`HtmlParser` предоставляет async-интерфейс, внутри которого синхронная операция парсинга выполняется через `executor`.

Это позволяет `event loop` продолжать выполнение других async-задач во время работы HTML parser.

На текущем этапе `AnalyzerService` обрабатывает результат следующим образом:
```text
fetch result  ->  await parser.parse(...)  ->  save result  ->  next fetch result
```
Несмотря на наличие нескольких `max_workers` у `ThreadPoolExecutor`, 
текущий workflow ожидает завершения `parser.parse(...)` перед обработкой следующего результата.

Поэтому в рамках __одной задачи__ анализа одновременно выполняется __только одна__ операция парсинга.

Данный подход является _временным_ решением для __MVP__.

---


## Результаты

### Положительные

- синхронный HTML-парсинг не блокирует `asyncio event loop`;
- HTTP и другие async-задачи могут продолжать выполняться во время парсинга;
- `HtmlParser` предоставляет async-интерфейс для `Service layer`;
- реализация остается относительно простой для MVP;
- архитектура допускает дальнейшее развитие в полноценный `pipeline`.


### Отрицательные

- возможности `ThreadPoolExecutor` используются не полностью;
- HTML parsing внутри одной задачи фактически выполняется последовательно;
- отсутствует независимая конкурентная обработка нескольких результатов парсером.


### Ограничения

Текущая реализация не является полноценным многопоточным `pipeline`.  
Несмотря на наличие `ThreadPoolExecutor(max_workers=N)` это не означает, 
одновременного выполняются N операций парсинга.

Для этого несколько parse tasks должны быть отправлены в `executor` без ожидания каждой из них.

---


## Заметки

После MVP планируется перейти к полноценному pipeline:

Fetch
  ↓
Parse
  ↓
Persist

с возможностью одновременной обработки нескольких URL на разных этапах.

Pipeline должен отдельно учитывать:

ограничение количества concurrent parse tasks;
backpressure;
обработку ошибок;
корректное завершение worker tasks;
обновление progress;
сохранение результатов в PostgreSQL.

### Выполнять HTML-парсинг непосредственно в Event Loop

__Преимущества__:
- наиболее простая реализация;
- не требуется `ThreadPoolExecutor`.

__Недостатки__:
- синхронный парсинг блокирует `event loop`;
- может задерживать выполнение HTTP-запросов и других async-задач.


### Сразу реализовать полноценный pipeline

__Преимущества__:
- несколько HTML-документов могут парситься одновременно;
- полноценное использование `ThreadPoolExecutor`;
- `fetch` и `parse` могут выполняться независимо.

__Недостатки__:
- существенно сложнее реализация;
- требуется управление очередями и ограничение размера очередей;
- усложняется обработка ошибок и lifecycle;
- избыточно для текущего этапа __MVP__.
