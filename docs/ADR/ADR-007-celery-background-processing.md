# ADR-007: Фоновое выполнение анализа через Celery

---

## Причина

Анализ списка URL является длительной операцией и включает:
- загрузку внешних ресурсов;
- HTML-парсинг;
- работу с Redis;
- сохранение результатов в PostgreSQL;
- обновление состояния и прогресса задачи.

Выполнение полного анализа внутри `HTTP request lifecycle` 
привязывало бы длительность запроса к длительности обработки всех URL.

Необходимо отделить создание задачи через API от ее фактического выполнения 
и выполнять анализ независимо от `FastAPI request`.

---

## Принятое решение

Использовать `Celery` для фонового выполнения задач анализа.

FastAPI отвечает за:
- прием и валидацию запроса;
- создание задачи анализа;
- сохранение исходных данных;
- отправку задачи в Celery;
- возврат `task_id` клиенту.

`Celery worker` выполняет непосредственно анализ:
```text
Client  ->  FastAPI  ->  Create AnalysisTask  ->  

-> Celery Queue  ->  Celery Worker  ->  AnalyzerService  ->

-> Fetch  ->  Parse  ->  Persist
```

В качестве `Celery broker` используется `Redis`.

`Celery task` должна оставаться тонкой точкой входа и не содержать бизнес-логику анализа.

Основной `workflow` остается в `AnalyzerService`, который может использоваться из разных точек входа:
```text
FastAPI / OPS ──┐
                ├──> AnalyzerService
Celery Worker ──┘
```

---

## Результаты

### Положительные
- `HTTP request` не ожидает завершения анализа;
- анализ выполняется независимо от lifecycle `FastAPI request`;
- `API` и `background processing` разделены;
- `worker` можно запускать и масштабировать отдельно;
- бизнес-логика остается в `Service layer`;
- `Celery` позволяет в дальнейшем использовать периодические задачи.

### Отрицательные
- появляется дополнительный инфраструктурный компонент;
- требуется `Celery worker`;
- требуется брокер сообщений;
- усложняется локальный запуск и разработка приложения.

### Ограничения
`Celery` отвечает за постановку и выполнение фоновой задачи.  
Анализ физически выполняется в процессе `Celery worker`, 
однако бизнес-логика анализа остается в `AnalyzerService`.  
`Celery task` является тонкой точкой входа в бизнес-сценарий.

Состояние анализа и его progress хранятся на уровне приложения в `PostgreSQL` 
и не должны зависеть только от состояния `Celery task`.

## Заметки

Для Celery используются отдельные логические БД Redis:
```text
Redis instance
├── DB 0 -> Celery broker
├── DB 1 -> Celery result backend
└── DB 2 -> Analysis Cache
```

## Возможные альтернативы

### FastAPI BackgroundTasks
__Преимущества__:
- простая реализация;
- не требуется отдельная очередь задач.

__Недостатки__:
- выполнение связано с процессом FastAPI;
- нет полноценной очереди и независимого `worker`;
- хуже подходит для длительных задач.


### Через `asyncio.create_task()`
__Преимущества__:
- минимальная дополнительная инфраструктура;
- естественно интегрируется с async-кодом.

__Недостатки__:
- задача остается внутри процесса FastAPI;
- потеря процесса приводит к потере выполняемой задачи;
- нет отдельной очереди и `worker infrastructure`.
