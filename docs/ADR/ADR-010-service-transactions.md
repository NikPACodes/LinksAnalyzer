# ADR-010: Управление commit и rollback на уровне Service

---

## Причина

В рамках одного бизнес-сценария `AnalyzerService` может выполнять 
несколько связанных операций через разные `repositories`.
Например, создание задачи требует сохранить `AnalysisTask` 
и предварительные `WebsiteResult` для всех URL.

Если каждый `repository` самостоятельно выполняет `commit`, 
`Service layer` теряет возможность управлять этими операциями как единым бизнес-сценарием.

Необходимо определить единое место, ответственное за границы транзакций.

---


## Принятое решение

Управление `commit` и `rollback` выполняется на уровне `Service layer`.

`AnalyzerService` получает готовую `AsyncSession` и передает ее всем `repositories`, участвующим в сценарии:
```text
AnalyzerService -> общая AsyncSession
  ├── TaskRepository
  ├── WebsiteResultRepository
  └── commit / rollback
```

`Repositories` выполняют операции доступа к данным и при необходимости вызывают `flush`, 
но не управляют `commit` и `rollback`.

`Flush` отправляет изменения в БД внутри текущей транзакции, но не фиксирует их окончательно.

При создании задачи сервис:
- создает `AnalysisTask`;
- создает предварительные `WebsiteResult`;
- выполняет `commit` после успешного выполнения обеих операций;
- при ошибке до фиксации выполняет `rollback`.

При длительном анализе сервис может выполнять несколько промежуточных коммитов для сохранения прогресса. 
Границы транзакций определяются сценарием, а не отдельными repository-методами.

---


## Результаты

### Положительные
- операции нескольких `repositories` объединяются в одну транзакцию;
- правила сохранения находятся рядом с бизнес-логикой;
- repositories переиспользуются в разных сценариях;
- FastAPI и Celery используют общую логику управления транзакциями.

### Отрицательные
- `Service layer` получает дополнительную ответственность за управление транзакциями;
- при сложных сценариях необходимо явно контролировать места выполнения `commit`.

### Ограничения
`Repository` не должен самостоятельно выполнять `commit`.

Все `repositories` одной транзакции должны использовать общую `AsyncSession`.

`Rollback` отменяет только изменения текущей незавершенной транзакции и не затрагивает ранее выполненные коммиты.

---


## Заметки
`flush` и `commit` выполняют разные задачи:
- `flush` позволяет отправить накопленные изменения в PostgreSQL внутри текущей транзакции, не завершая ее;
- `commit` фиксирует транзакцию и делает изменения постоянными.

## Возможные альтернативы

### Commit внутри каждого Repository
__Преимущества__:
- repository самостоятельно завершает каждую операцию;
- вызывающему коду требуется меньше управления транзакциями.

__Недостатки__:
- сложнее объединять операции разных `repositories` в одну транзакцию;
- ошибка последующей операции оставляет ранее сохраненные частичные данные.

### Commit на уровне API / Celery task
__Преимущества__:
- сервис освобождается от явных `commit` и `rollback`.

__Недостатки__:
- правила сохранения приходится поддерживать в разных точках входа;
- `API` и `Celery task` должны знать границы бизнес-операций;
- `Service` перестает полностью контролировать выполнение бизнес-сценария.
