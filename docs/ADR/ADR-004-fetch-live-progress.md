# ADR-004: Конкурентная загрузка URL для Live Progress

---


## Причина

Анализатор должен выполнять HTTP-запросы к нескольким URL конкурентно 
и отображать live progress выполнения задачи.

Первоначальный подход с `fetch_many()` позволял конкурентно загружать URL, 
но возвращал результаты только после завершения всех запросов.

Из-за этого уже завершенные запросы нельзя было сразу передать на дальнейшую обработку, 
а processed_urls и progress задачи обновлялись только после завершения всего batch.

Для реализации live progress необходимо получать каждый FetchResult сразу 
после завершения соответствующего HTTP-запроса.

При этом `fetch_many()` остается полезным для сценариев, 
где необходимо получить все результаты целиком и сохранить порядок исходных URL.

---


## Принятое решение

Сделать в `WebsiteFetcher` два метода:
```python
fetch_many(...)
fetch_many_iter(...)
```

Оба метода выполняют HTTP-запросы конкурентно, но отличаются способом возврата результатов.


### fetch_many
Использует `asyncio.gather()` и возвращает результаты после завершения всех HTTP-запросов.

Основные свойства:
- запросы выполняются конкурентно;
- метод ожидает завершения всего набора;
- результаты возвращаются одним списком;
- порядок результатов соответствует порядку исходных URL.

Метод подходит для случаев, когда необходимо получить весь набор результатов целиком 
с сохранением порядка URLs.


### fetch_many_iter
Использует `asyncio.as_completed()` и возвращает результаты по мере завершения запросов.

Основные свойства:
- запросы выполняются конкурентно;
- результат становится доступен сразу после завершения конкретного запроса;
- порядок результатов зависит от времени завершения запросов;
- нет необходимости ожидать завершения всего набора.

Основной workflow `AnalyzerService` использует `fetch_many_iter()` для поддержки live progress.  
Таким образом, progress задачи может обновляться по мере обработки отдельных URL, 
пока остальные HTTP-запросы еще выполняются.

---


## Результаты

### Положительные
- HTTP-запросы выполняются конкурентно;
- реализована возможность live progress;
- можно получать результаты по мере их готовности;
- медленные URL не задерживают обработку уже загруженных
- `fetch_many()` остается доступным для сценариев, где нужен полный набор результатов.

### Отрицательные
- поддерживаются два похожих метода загрузки;
- при использовании `fetch_many_iter()` порядок результатов не соответствует порядку входных URL.

### Ограничения
`fetch_many_iter()` определяет только способ получения результатов HTTP-загрузки.

---


## Заметки

`fetch_many()` и `fetch_many_iter()` отличаются не уровнем конкурентности HTTP-запросов, 
а способом получения результатов.

```text
fetch_many       -> дождаться всех  -> возвращает список
fetch_many_iter  -> результат готов -> сразу возвращает yield
```
`fetch_many_iter()` был добавлен прежде всего для реализации live progress задачи.

---


## Возможные альтернативы

### Оставить только `fetch_many()`
__Преимущества__:
- проще интерфейс `WebsiteFetcher`;
- результаты сохраняют порядок входных URL.

__Недостатки__:
- обработка начинается только после завершения всех HTTP-запросов;
- медленные URL задерживают начало обработки уже полученных результатов;
- невозможно корректно обновлять live progress по мере завершения отдельных URL.

### Оставить только `fetch_many_iter()`
__Преимущества__:
- результаты доступны по мере готовности;
- подходит для основного workflow с live progress.

__Недостатки__:
- отсутствует простой метод для получения всех результатов одним списком;
- порядок завершения запросов не соответствует порядку исходных URL.
