# ADR-001: Структура проекта

---


## Причина

Проект содержит различные типы компонентов:
- публичные endpoints;
- служебные endpoints;
- бизнес-логику;
- Postgres;
- Redis;
- Celery worker;
- HTTP загрузчик;
- HTML парсер.

По мере развития проекта структура будет расширяться и усложняться, 
что будет приводить к усложнению разработки. 

---


## Принятое решение

Использовать модульную структуру приложения с layered architecture внутри бизнес-модулей.

Архитектура строится на двух уровнях:
- верхний уровень разделяет приложение на функциональные и инфраструктурные модули;
- внутри бизнес-модуля используется разделение по архитектурным слоям.

Структура верхнего уровня:
```text
app/
├── analyzer/
├── core/    
├── db/      
├── ops/     
└── worker/  
```

__analyzer__ рассматривается как отдельное приложение или функциональный модуль, 
внутри которого сохраняется разделение на API, Service и Repository layers.


### analyzer
Модуль анализа URL.

Разделение по архитектурным слоям:
```text
app/analyzer/
├── api/            # HTTP endpoints, API
├── repositories/   # работа с данными  Postgres
├── schemas/        # API-схемы запросов и ответов
├── services/       # бизнес-сценарии и оркестрация
├── cache.py        # работа с кэшем
├── dto.py          # внутренние структуры
├── fetcher.py      # загрузчик HTTP
├── models.py       # ORM-модели
└── parser.py       # парсинг HTML
```


### core
Общая инфраструктура и конфигурация приложения:
- application settings;
- конфигурация подключений;
- общие инфраструктурные настройки.


### db
Общая инфраструктура работы с БД:
- SQLAlchemy Base;
- создание async engine;
- фабрики AsyncSession;
- управление lifecycle database resources.


### ops
Отдельный служебный модуль приложения.

Содержит endpoints для диагностики и разработки:
- health checks;
- проверки PostgreSQL, Redis и Celery;
- служебные операции.


### worker
Инфраструктура фонового выполнения задач:
- конфигурацию Celery application;
- настройки очередей и worker;
- инфраструктурные компоненты запуска background jobs.

---


## Результат

### Положительные
- функциональность анализатора имеет явную границу;
- business layer отделен от transport и persistence;
- infrastructure modules не смешиваются с analyzer;
- новый функциональный модуль можно добавить по аналогичной схеме;
- подход остается знакомым разработчикам с опытом Django.


### Отрицательные
- архитектура становится сложнее простого глобального layered-проекта;
- необходимо контролировать направление зависимостей;
- не каждый небольшой компонент требует отдельного слоя.

---


## Заметки

При появлении новых крупных функциональных областей они могут быть оформлены отдельными модулями:
```text
app/
├── analyzer/
├── crawler/
├── scheduler/
├── ...
├── core/
├── db/
├── ops/
└── worker/
```

Каждый такой модуль может иметь собственные:
```text
api/
services/
repositories/
schemas/
models/
```

При этом каждый бизнес-модуль допускает собственную структуру.

---


## Возможные альтернативы

### Глобальная layered architecture
```text
app/
├── api/
├── services/
├── repositories/
├── schemas/
└── models/
```

__Преимущества__:
- простая начальная структура;
- легко понять в небольшом проекте;
- привычное разделение по техническим слоям.

__Недостатки__:
- код одного функционального модуля распределяется по всему проекту;
- при появлении новых областей глобальные директории быстро растут;
- сложнее определить принадлежность service/repository/schema к конкретному модулю;
- увеличивается связанность между функциональными областями.

### Модульная структура без внутренних слоев
```text
app/
├── analyzer/
├── users/
└── reports/
```

__Преимущества__:
- минимальная глубина директорий;
- подходит для маленьких модулей.

__Недостатки__:
- при росте функциональности модуль быстро становится перегруженным;
- хуже разделяются API, бизнес-логика, хранение и работа с данными.




















Использовать feature-based структуру приложения.

Основная бизнес-функциональность анализа размещается внутри:

```text
app/analyzer/
```

Структура приложения:
```text
app/
├── analyzer/
│   ├── api/
│   ├── repositories/
│   ├── schemas/
│   ├── services/
│   ├── cache.py
│   ├── dto.py
│   ├── fetcher.py
│   ├── models.py
│   └── parser.py
│
├── core/
├── db/
├── ops/
└── worker/
```

Внутри analyzer используется дополнительное разделение по техническим
слоям.
Ответственность модулей:
- analyzer — бизнес-функциональность анализа сайтов;
- core — конфигурация и общая инфраструктура;
- db — создание и управление database session;
- ops — служебные и диагностические endpoints;
- worker — конфигурация фонового выполнения.


## Alternatives considered
Глобальная layered architecture
app/
├── api/
├── services/
├── repositories/
├── schemas/
└── models/
Преимущества:
- простая начальная структура;
- привычное разделение по техническим слоям.
Недостатки:
- функциональность одного домена распределяется по всему проекту;
- сложнее расширять проект дополнительными функциональными модулями;
- со временем директории верхнего уровня становятся перегруженными.
Feature-based architecture
Преимущества:
- функциональность анализатора локализована;
- проще определять границы ответственности;
- удобнее дальнейшее расширение проекта.
Недостатки:
- структура немного сложнее для маленького приложения.


## Consequences
Положительные
- бизнес-модуль анализатора имеет явную границу;
- инфраструктурные endpoints отделены от публичного API;
- проще расширять проект новыми функциональными модулями;
- зависимости компонентов становятся понятнее.
Отрицательные
- часть технических слоев существует внутри feature-модуля;
- требуется контролировать направление зависимостей между пакетами.
Notes
При появлении новых крупных возможностей они могут быть оформлены как
отдельные feature-модули без изменения структуры analyzer.
