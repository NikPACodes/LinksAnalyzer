# ADR-002: Выделение служебного OPS API

---


## Причина

Приложению необходимы технические endpoints, которые не относятся к публичному бизнес-API:
- health check приложения;
- проверка PostgreSQL;
- проверка Redis;
- проверка Celery;
- служебные операции;
- ручной запуск обработки задачи для разработки и отладки.

Размещение таких endpoints внутри `/api/v1` смешивало бы публичный API приложения 
и внутренние операционные инструменты.

---


## Принятое решение

Выделить служебные endpoints в отдельный модуль:
```text
app/ops/
```
и отдельное URL-пространство:
```text
/api/ops/*
```

По итогу получаем:
- публичный API (с привязкой к версионированию) `/api/v1/*` 
- служебные API (без привязки к версиям) `/api/ops/*`

__OPS API__ предназначен для:
- диагностики инфраструктуры;
- разработки и отладки;
- внутренних технических операций.

__OPS endpoints__ не должны дублировать бизнес-логику и должны использовать существующий Service layer.

---


## Результаты

### Положительные
- публичный API остается чистым;
- служебные endpoints имеют явную границу;
- OPS API можно независимо расширять;
- доступ к OPS endpoints можно отдельно ограничить.

### Ограничения
В production доступ к OPS API `/api/ops` необходимо ограничить в доступе и контролировать отдельно.

### Отрицательные
- появляется дополнительный модуль OPS API;
- необходимо разделять endpoint на основные и служебные API.

---


## Заметки

Префикс `/api/ops` является архитектурным разделением, а не механизмом безопасности.

---


## Возможные альтернативы

### Не выделять служебные endpoints в отдельный модуль

__Преимущества__:
- проще структура;
- меньше routers.

__Недостатки__:
- технические endpoints смешиваются с бизнес-API;
- версионирование API начинает затрагивать служебные endpoints.
