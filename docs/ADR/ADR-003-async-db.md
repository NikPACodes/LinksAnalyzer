# ADR-003: Асинхронная работа с БД PostgreSQL

---


## Причина

Приложение построено на асинхронном стеке FastAPI и выполняет большое количество I/O операций:
- HTTP-запросы к анализируемым ресурсам;
- запросы к PostgreSQL;
- работу с Redis.

Синхронные обращения к БД могут блокировать event loop во время ожидания ответа PostgreSQL.

Также необходимо определить единый подход к созданию и использованию database sessions между слоями приложения.

---


## Принятое решение

Для работы с PostgreSQL использовать асинхронный стек:
- SQLAlchemy Async;
- `AsyncEngine`;
- `AsyncSession`;
- `asyncpg`.

Общая инфраструктура подключения к БД располагается в:
```text
app/db/
```

Для FastAPI `AsyncSession` создается через dependency и передается по слоям:
```text
API -> Service -> Repository -> PostgreSQL
```

__Service__ и __Repository__ не создают собственные sessions, а получают уже созданную `AsyncSession`.  

__Repositories__ используют session для выполнения операций с данными и при необходимости вызывают `flush()`.

__Service__ использует session для управления `commit()` и `rollback()`, координирует бизнес-сценарий 
и может использовать несколько repositories в рамках одной транзакции.

`AsyncSession` не должна одновременно использоваться несколькими независимыми asyncio tasks.

Для Celery worker используется отдельная database infrastructure с собственным lifecycle подключения, 
поскольку FastAPI и Celery работают в разных runtime/event loop contexts.

---


## Результаты

### Положительные
- обращения к PostgreSQL не блокируют event loop во время ожидания I/O;
- сохраняется единый async-подход приложения;
- создание и lifecycle `AsyncSession` отделены от Repository и Service;
- несколько repositories могут использовать одну session в рамках бизнес-сценария;
- управление транзакцией остается на уровне Service.

### Отрицательные
- инфраструктура async database сложнее синхронного варианта;
- необходимо корректно управлять lifecycle `AsyncSession`;
- необходимо учитывать ограничения использования async resources между разными event loops.

### Ограничения
Одна `AsyncSession` не предназначена для конкурентного использования несколькими независимыми asyncio tasks.
Async database resources FastAPI нельзя напрямую переиспользовать внутри Celery worker.

---


## Заметки

Отдельное подключение к БД для Celery worker и причины его появления описываются в отдельном ADR.
Управление `commit()` и `rollback()` на уровне Service позволяет Repository 
оставаться ответственным только за операции доступа к данным.

---


## Возможные альтернативы

### Синхронный SQLAlchemy
__Преимущества__:
- проще lifecycle подключения;
- проще реализация и отладка.

__Недостатки__:
- database I/O может блокировать event loop;
- не соответствует общей async-архитектуре приложения.

### Создание session внутри каждого Repository
__Преимущества__:
- Repository самостоятельно управляет своим подключением.

__Недостатки__:
- сложнее объединять операции нескольких repositories в одну транзакцию;
- Repository начинает управлять lifecycle инфраструктурного ресурса;
- усложняется контроль `commit()` и `rollback()`.
