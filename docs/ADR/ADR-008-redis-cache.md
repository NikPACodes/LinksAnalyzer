# ADR-008: Кэширование результатов анализа URL в Redis

---

## Причина

Один и тот же URL может анализироваться повторно в разных задачах.

Без кэширования каждый повторный анализ требует заново:
- выполнить HTTP-запрос;
- получить HTML;
- выполнить парсинг страницы.

Это создает лишние HTTP-запросы к внешним ресурсам и увеличивает время обработки задачи.  
При этом PostgreSQL используется для хранения результатов конкретных задач и истории анализа,  
поэтому использовать его как временный кэш нецелесообразно.

---


## Принятое решение

Использовать Redis для временного кэширования успешно полученных результатов анализа URL.

Для application cache используется отдельная `Redis logical database`:
```text
Redis DB 2 -> Analysis Cache
```

Кэшируется готовый результат анализа, а не исходный HTML:
```text
URL  ->  Fetch  ->  Parse  ->  CachedAnalysisResult  ->  Redis
```

Ключ кэша формируется на основе `SHA-256` от URL:
```text
{prefix}:{sha256(url)}
```
Для записей используется `TTL`, после истечения которого URL должен быть проанализирован повторно.

В кэш сохраняются только успешно обработанные результаты с успешно выполненным HTML-парсингом.  
Ошибки загрузки, парсинга не кэшируются.

Перед HTTP-загрузкой `AnalyzerService` проверяет наличие результата в Redis:
```text
Cache lookup
 ├── HIT  -> сохранить cached result в результат задачи
 └── MISS -> Fetch -> Parse -> Cache -> сохранить результат
                        │
                        └── если результат cacheable -> Cache
```

Недоступность Redis или ошибка чтения кэша рассматривается как `cache miss` 
и не должна приводить к завершению задачи анализа с ошибкой.

PostgreSQL остается основным хранилищем результатов конкретных задач.

---


## Результаты

### Положительные
- уменьшается количество повторных HTTP-запросов и операций парсинга;
- результаты переиспользуются между задачами и worker-процессами;
- `TTL` ограничивает время использования устаревших данных;
- отказ `application cache` не останавливает основной `workflow`;
- история результатов задач сохраняется в PostgreSQL независимо от срока жизни кэша.


### Отрицательные
- до истечения `TTL` результат может не отражать изменения страницы;
- обращения к Redis добавляют задержку при отсутствии записи и при ошибках подключения;
- требуется управление `TTL` и `invalidation`.


### Ограничения
Кэш является временной оптимизацией и не используется как постоянное хранилище результатов.

В кэш не сохраняются:
- ошибки HTTP-загрузки;
- результаты с ошибкой HTML-парсинга.

После истечения `TTL` выполняется повторный анализ URL.

---


## Заметки

Redis используется приложением для нескольких независимых задач:
```text
Redis instance
├── DB 0 -> Celery broker
├── DB 1 -> Celery result backend
└── DB 2 -> Analysis Cache
```

Для разделения ключей `application cache` также используется собственный `prefix`.

Текущий `TTL` кэша задается через `application settings`.

---


## Возможные альтернативы

### Не использовать кэш
__Преимущества__:
- проще архитектура;
- каждый анализ получает актуальные данные страницы.

__Недостатки__:
- повторные HTTP-запросы для одинаковых URL;
- повторный HTML-парсинг;
- увеличение времени обработки.


### Использовать PostgreSQL как кэш
__Преимущества__:
- не требуется дополнительное хранилище;
- результаты уже сохраняются в PostgreSQL.

__Недостатки__:
- смешивается постоянное хранение результатов и временное кэширование;
- требуется дополнительная логика поиска актуального результата;
- сложнее управлять `TTL` и `invalidation`.
